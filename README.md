# CLIProxyAPI Billing Bot

Telegram-бот для ручного распределения общей стоимости подписок по использованию
ключей CPA Usage Keeper. Бот не управляет ключами CLIProxyAPI, не принимает
деньги и не подтверждает перевод автоматически. Он ведёт начисления, баланс,
авансы и скриншоты на ручной проверке администратора.

## Возможности

- Владелец пишет боту /start, отправляет действующий API-ключ и при необходимости
  добавляет другие ключи. Один ключ закрепляется за одним Telegram ID. Секрет
  сверяется с Keeper в памяти и не записывается в базу; сообщение с ключом
  удаляется из личного чата после получения.
- Администратор вручную запускает расчёт, вводит сумму подписки в USD, процент
  банковской комиссии и курс RUB за USD, видит черновик и подтверждает его.
- Использование всех ключей, в том числе пока непривязанных, участвует в
  распределении. У непривязанного ключа начисление ждёт владельца. При поздней
  привязке оно сразу появляется в истории и балансе человека; чужие начисления
  не пересчитываются.
- Человек видит долг в USD и RUB, историю начислений и платежей. Для оплаты он
  выбирает валюту, полную или произвольную сумму, отправляет скриншот. Админ
  подтверждает или отклоняет его. Произвольная сумма позволяет платить частями
  и заранее.
- Админ может занести ранее полученный платёж или аванс без скриншота.
- Админ видит непривязанные начисления и историю конкретного участника с датами
  начислений и платежей.

## Правила расчёта

Расчёт использует полные календарные дни Europe/Moscow. Запуск 26 сентября
покрывает дни по 25 сентября включительно. Начало первого периода админ вводит
один раз; всё до него считается урегулированным вне бота. Следующий период
начинается на следующий день после конца опубликованного расчёта. Дата
фактической оплаты человека на границы периодов не влияет.

Бот запрашивает у Keeper защищённые endpoints:

- GET /usage/api-keys — действующие ключи;
- GET /usage/api-keys/settings — секреты действующих ключей только для проверки
  присланного участником ключа;
- GET /usage/analysis?range=custom&unit=day&start=YYYY-MM-DD&end=YYYY-MM-DD —
  стоимость и число запросов по ключам.

Сумма Keeper в USD — оценка стоимости использования для распределения
подписки, а не сама сумма к оплате. Keeper применяет цены моделей и
настроенные множители, включая быстрый режим. Бот не повторяет эту формулу.
Незнакомая цена модели останавливает создание черновика; после настройки цены
в Keeper админ запускает расчёт заново. Бесплатная модель должна иметь
известную нулевую цену. Нулевое суммарное платное использование тоже ошибка.

Админская сумма подписки распределяется пропорционально стоимости
использования. Затем к общей сумме добавляется банковская комиссия и
распределяется по тем же ключам. Только потом итог переводится в RUB по
введённому курсу. Суммы по ключам распределяются методом наибольших остатков
в целых центах и копейках: они точно сходятся с суммой расчёта. Например,
$400 и 1% дают к оплате $404; при курсе 80 это ₽32 320. Все параметры и
суммы сохраняются в опубликованном расчёте и больше не меняются.

В интерфейсе «счёт» — начисления и текущий баланс, а не отдельный платёжный
документ. Опубликованные начисления видны по периодам. Черновики в баланс не
попадают. Повторное подтверждение черновика не создаёт второй расчёт.

## Платежи и авансы

Только подтверждённые платежи влияют на баланс. Они гасят начисления от
самого старого периода к новому. Платёж в USD гасит долларовый остаток.
Рублёвый платёж гасит рублёвый эквивалент того же начисления по курсу,
зафиксированному в его расчёте. Остаток RUB или USD сохраняется авансом
в исходной валюте, без пересчёта по сегодняшнему курсу. Когда появится новое
начисление, аванс применяется по его курсу. При поздней привязке ключа
распределения подтверждённых платежей перестраиваются по тому же правилу FIFO.

Каждое начисление хранит USD и RUB сумму. Например, $10 + 1% при курсе ₽80
становится $10.10 / ₽808. Следующее $10 + 1% при курсе ₽90 становится
$10.10 / ₽909. Общий долг: $20.20 или ₽1717. После подтверждённых ₽400 и $8
остаётся $7.20 / ₽648: сначала закрыто старое начисление, затем часть нового.

Платежи и начисления учитываются в целых центах и копейках. При очень мелких
частичных платежах менее стоимости одного цента остаток может временно
показываться одновременно как RUB аванс и USD долг: бот не зачитывает часть
цента. Следующий платёж или начисление обычно погасит этот остаток.

## Хранение

SQLite через SQLAlchemy 2 с async-драйвером. Таблицы:

- users и key_ownerships: Telegram ID и ID ключей Keeper, без секретов;
- billing_runs: период, общая сумма, комиссия, курс, черновик/публикация;
- key_charges: неизменяемые начисления по ключам в USD и RUB;
- payments: валюта, фактическая сумма, статус, ссылка на скриншот Telegram;
- payment_allocations: сколько подтверждённого платежа погасило каждое
  начисление.

Баланс вычисляется из начислений и распределений; его нельзя случайно
перезаписать отдельным числом. Бот рассчитан на один запущенный процесс.
Новая база создаётся автоматически. Для будущих изменений схемы понадобятся
миграции; текущая версия не меняет существующую схему сама.

## Подготовка

Нужны Python 3.12+ и uv. Создайте бота через BotFather и узнайте числовой
Telegram ID администратора. Администратор должен сначала открыть личный чат с
ботом. Нужен пароль входа CPA Usage Keeper (LOGIN_PASSWORD), а в CLIProxyAPI
должен быть включён сбор usage.

~~~bash
cp .env.example .env
uv sync --group dev
uv run --env-file .env cliproxy-billing-bot
~~~

Замените значения в .env:

| Переменная | Назначение |
| --- | --- |
| TELEGRAM_BOT_TOKEN | токен бота |
| ADMIN_TELEGRAM_IDS | один или несколько Telegram ID через запятую |
| KEEPER_BASE_URL | URL Keeper, заканчивающийся на /usage/api/v1 |
| KEEPER_LOGIN_PASSWORD | пароль администратора Keeper |
| DATABASE_URL | SQLite URL, по умолчанию sqlite+aiosqlite:///./billing.db |
| TIME_ZONE | часовой пояс расчётов, по умолчанию Europe/Moscow |

Пример .env.example предполагает запуск рядом с Keeper во внутренней сети
Podman. Для локальной проверки с другой машины используйте доступный по HTTPS
URL Keeper, например https://cli.neutrino.su/usage/api/v1, и отдельный
локальный billing.db. Никакого деплоя настройка не выполняет.

## Контейнер и CI

`Dockerfile` собирает образ с Python 3.12 через зафиксированный `uv.lock` и
запускает бота от UID/GID 10001. База по умолчанию находится по адресу
`sqlite+aiosqlite:////data/billing.db`. При запуске контейнера подключите
постоянное хранилище к `/data` с правом записи для UID 10001. Не запускайте
несколько экземпляров бота одновременно: long polling Telegram и SQLite
рассчитаны на один процесс. Токен Telegram, пароль Keeper и ID админов
передавайте переменными окружения; они не входят в образ.

GitHub Actions на PR и push в `main` выполняет Ruff, pyright, pytest и сборку
контейнера. После успешного push в `main` он публикует образ в GHCR с тегами
`main` и `sha-…`, затем вызывает Reploy для образа `:main`. Имя образа берётся
из имени GitHub-репозитория и приводится к нижнему регистру. Ручной запуск
workflow выполняет только проверки и сборку, без публикации и Reploy.

Для фактического обновления подготовьте на сервере работающий Podman-сервис
с этим образом, постоянным `/data`, доступом к Keeper и нужными переменными
окружения. Reploy обновляет уже существующий сервис; сам workflow его не
создаёт. В GitHub environment `production` задайте переменную `REPLOY_URL`
(полный HTTPS URL endpoint `/deploy`) и секрет `REPLOY_TOKEN`, выпущенный на
сервере с разрешением только на тег образа `:main`. Для отправки образа в GHCR
workflow использует штатный `GITHUB_TOKEN` с правом `packages: write`.

## Сценарии Telegram

Участник: /start → ключ. Во время ввода ключа клавиатура показывает только
«Отмена»; после привязки появляются «Баланс», «История», «Мои ключи»,
«Добавить ключ», «Оплатить». При оплате клавиатура меняется по шагам:
USD/RUB/«Отмена» → «Погасить всё» или «Другая сумма / аванс»/«Отмена» →
ввод суммы или скриншота с одной кнопкой «Отмена». На шаге выбора суммы можно
сразу отправить число в чат, без нажатия «Другая сумма / аванс». После скриншота
возвращается главное меню. Способ перевода участники согласуют с админом вне бота.
Если бот перезапустился и потерял шаг диалога, на неизвестное сообщение он
ответит подсказкой и восстановит главное меню.

При запуске бот очищает список команд Telegram для всех пользователей и админов.
Команда /start остаётся входом в бот, а /cancel по-прежнему отменяет текущий ввод,
если набрать её вручную.

Админу дополнительно доступна кнопка «Управление» с отдельной клавиатурой:
«Новый расчёт», «Черновик», «Проверить оплаты», «Участники»,
«Непривязанные начисления», «Занести платёж / аванс» и возврат в главное меню.
В первый раз бот попросит дату начала.
После ввода суммы, комиссии и курса появится черновик со всеми ключами,
включая непривязанные. «Опубликовать расчёт» фиксирует начисления и уведомляет
зарегистрированных владельцев. Раздел «Проверить оплаты» позволяет открыть
нерассмотренные скриншоты повторно. «Участники» показывает Telegram ID для
ручного внесения старого платежа или аванса. Список разбит на страницы по восемь
человек: стрелки листают страницы, кнопка участника открывает его историю, а
возврат из истории ведёт на ту же страницу.
«Непривязанные начисления» — долги ещё не привязанных ключей. Отмена ввода не
удаляет сохранённый черновик; удалить его можно из «Управления».

## Проверка

~~~bash
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest -q
~~~

Тесты проверяют распределение центов, комиссию и курс, позднюю привязку,
смешанные валюты, авансы, отклонённые платежи и ответы Keeper. Интеграционный
запуск с реальным Telegram и Keeper требует токена и пароля и намеренно не
выполняется автоматически.
